\begin{center}
    {\fontsize{12}{14}\selectfont\bfseries RESUMO}
\end{center}
{\espacosimples
\noindent O presente trabalho descreve o protótipo RadarTorres, um sistema para detecção,
localização e seleção automática de ação por sensoriamento, desenvolvido como Trabalho de
Conclusão de Curso em Engenharia da Computação. O protótipo integra sensores para identificar
objetos em um ambiente monitorado, registrar seu posicionamento e permitir o acionamento manual
ou automático de dispositivos de resposta. Este trabalho detalha o modelo de dados da aplicação:
atualmente a persistência é feita em arquivos CSV organizados por usuário do sistema operacional,
contemplando seis tabelas -- usuários, objetos detectados, ações realizadas, alterações de modo,
preferências de usuário e chamados de ajuda --, cada uma acessada por meio de uma interface de
repositório dedicada. Essa escolha, registrada na documentação técnica do projeto, mantém o
sistema simples nesta fase e sinaliza explicitamente a intenção de migração futura para um banco
de dados relacional. Descreve-se a estrutura atual das tabelas, suas relações (por login, sem
chaves estrangeiras reais) e o modelo proposto para a migração para SQL, no qual as referências
textuais seriam substituídas por chaves estrangeiras íntegras, sem necessidade de alterar as
camadas de ViewModel ou Service da aplicação, já que dependem apenas das interfaces de
repositório. Os resultados indicam que a arquitetura baseada em interfaces viabiliza essa
migração de forma incremental e de baixo risco.

\noindent\textbf{Palavras-chave}: Sensoriamento; Modelo de dados; Persistência; Migração para SQL; Protótipo.
\par}
\espacoumemeio

\begin{center}
    {\fontsize{12}{14}\selectfont\bfseries ABSTRACT}
\end{center}
{\espacosimples
\noindent This work describes the RadarTorres prototype, a system for automatic action
detection, localization and selection through sensing, developed as a Final Course Project in
Computer Engineering. The prototype integrates sensors to identify objects in a monitored
environment, register their position and allow manual or automatic activation of response
devices. This work details the application's data model: persistence is currently implemented
through CSV files organized per operating-system user, covering six tables -- users, detected
objects, executed actions, mode changes, user preferences and help tickets --, each accessed
through a dedicated repository interface. This choice, documented in the project's technical
records, keeps the system simple at this stage while explicitly signaling the intent to migrate
to a relational database in the future. The current table structure, its relationships (by
login, without real foreign keys) and the proposed model for the SQL migration are described,
in which textual references would be replaced by proper foreign keys, without requiring changes
to the application's ViewModel or Service layers, since they depend only on the repository
interfaces. Results indicate that the interface-based architecture enables this migration
incrementally and with low risk.

\noindent\textbf{Keywords}: Sensing; Data model; Persistence; SQL migration; Prototype.
\par}
\espacoumemeio

\subsection{Modelo de dados}

Na versão atual do protótipo não há um banco de dados relacional em uso: a persistência é feita
em arquivos CSV, decisão registrada explicitamente na documentação técnica do projeto, que
sinaliza a intenção de conversão futura para SQL. Os arquivos ficam em uma pasta por usuário do
Windows (\texttt{\%AppData\%$\backslash$RadarTorres$\backslash$Data$\backslash$}), um por
entidade, criados com cabeçalho na primeira execução. Cada tabela é acessada por uma interface de
repositório dedicada (por exemplo, \texttt{IUsuarioRepository}), o que permite trocar a
implementação em CSV por uma implementação em SQL sem alterar nenhuma camada de ViewModel ou
Service. A Tabela 1 resume as seis entidades identificadas.

    \begin{center}
    {\small Tabela 1: Entidades do modelo de dados (persistência em CSV)}\par
    \vspace{0.3em}
    \renewcommand{\arraystretch}{1.3}
    \begin{tabular}{p{3.7cm}p{8.8cm}}
        \hline
        \textbf{Entidade} & \textbf{Descrição} \\
        \hline

Não há integridade referencial imposta pelo armazenamento atual: campos como
\texttt{UsuarioResponsavel} e \texttt{UsuarioSolicitante} referenciam o login do usuário como
texto, validado apenas pelo código da aplicação, e não por uma chave estrangeira real.

Para a migração futura, propõe-se implementar uma versão SQL de cada repositório (por exemplo,
via Entity Framework Core), mantendo a mesma assinatura de método das interfaces já existentes, e
trocar apenas o registro da implementação no contêiner de injeção de dependência. Com um SGBD
relacional, as referências textuais por login passariam a ser chaves estrangeiras íntegras por
identificador numérico, e a relação entre \texttt{usuarios} e \texttt{preferencias\_usuario}
passaria a ter integridade garantida pelo próprio banco. Nenhuma dessas tabelas SQL, migration ou
arquivo de banco existe no repositório até o momento; trata-se de uma proposta baseada no
planejamento já documentado pela equipe do projeto.
